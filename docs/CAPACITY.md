# القدرة — الطريق لـ١٠ آلاف أوردر في اليوم

> الهدف اللي المالك حدده: **مش أقل من ١٠ آلاف أوردر/يوم**، والسيستم مايقعش بعد شهرين شغل.
> الملف ده بيقول **إيه اللي اتعمل**، و**إزاي تثبته بنفسك** بالأرقام مش بالكلام.

---

## المشكلة الأصلية

السيستم كان شغّال كويس على مئات الأوردرات. المشكلة إن أربع حاجات كانت بتكبر مع
حجم البيانات بدل ما تفضل ثابتة — يعني كل ما الشغل يزيد، السيستم يبطّأ، لحد ما يقف:

| # | الاختناق | كان بيعمل إيه |
|---|---|---|
| ١ | **رصيد التاجر** | كل تسليم بيمسح **دفتر التاجر كله + عهد كل المناديب** من أول يوم تشغيل — جوّه قفل الصف. تعقيد تربيعي. |
| ٢ | **الاستيراد المجمّع** | ٢٠٠٠ صف في ترانزاكشن واحدة (~٤٠ ألف استعلام) — وأول صف يفشل كان بيوقّع الباقي كله. |
| ٣ | **التقارير** | بتمسح كل الشحنات وكل سطور اليومية من غير أي حد ولا فترة. |
| ٤ | **الفهارس** | الشاشة الرئيسية = مسح كامل + فرز. البحث = مسح كامل. دفتر اليومية = مسح كامل. |

وفوقهم: مفيش مهلات على القاعدة (استعلام معلّق واحد = اتصال ضايع للأبد)،
وكشف الحساب كان بيفتح **ترانزاكشن كاتبة** في كل فتحة صفحة.

## اللي اتعمل

### ١) رصيد التاجر بقى تزايدي
`src/server/services/ledger.ts`

القيد بيضيف **دلتاه** بس على الرصيد المخزَّن، بدل ما يعيد حساب الدفتر:
- `applyBalanceDelta` — UPSERT بتكلفة ثابتة
- `isEntryPending` — القيد ده تحت التحصيل؟ (فحص على عهدة المندوب بس)
- `confirmPendingOnHandover` — تسليم العهدة بيقلب المعلّق لمؤكد للتجار المتأثرين بس

**الخانتان ومعناهما ما اتغيروش.** `recomputeMerchantBalance` اتساب للمطابقة والاسترجاع.

واتشالت إعادة الحساب الكاملة الزيادة من **٤ مسارات** كانت بتعملها فوق التزايدي:
تسليم العهدة · التسوية · تأكيد طلب الاستلام · اعتماد المطالبة.

**القياس** (`npm run bench:balance`):

| حجم الدفتر | إعادة حساب كاملة (القديم) | قيد تسليم (الجديد) |
|---|---|---|
| ٢٠٠ قيد | 12.4 ms | 12.7 ms |
| ١٬٠٠٠ قيد | 22.9 ms | 11.4 ms (٢×) |
| ٢٬٥٠٠ قيد | **48.3 ms** | **12.5 ms (٣.٩×)** |

القديم بيكبر مع الدفتر. الجديد ثابت. عند مليون شحنة الفرق مش ٤× — بيبقى مئات.

**الحارس**: `npm run verify:balance` بيعمل سلسلة عمليات حقيقية (تسليم كاش ·
إنستاباي · مندوبين مختلفين · مرتجع · تسليم عهدة · تسليم بعد العهدة · تسوية
واعتماد ودفع) و**بعد كل عملية** بيقارن المخزَّن بإعادة الحساب الكاملة.

**الشبكة تحته**: `npm run reconcile` كل ليلة — بيقارن **الخانتين** (مش الإجمالي
بس زي فحص `I4`) ويصلّح ويبلّغ.

### ٢) الاستيراد على دفعات مع نجاح جزئي
`src/server/services/imports.ts`

- كل ١٠٠ صف ترانزاكشن مستقلة بتتثبّت لوحدها (`IMPORT_CHUNK_SIZE`)
- كل صف جوّه **savepoint** — الصف الفاشل بيترجع لوحده والباقي بيكمّل
- التسعير والإعدادات بتتقرا **مرة واحدة** للدفعة كلها (`PricingCache`)
- القائمة السوداء استعلام واحد بدل واحد لكل صف

> **البق اللي اتصلّح**: قبل كده أول صف يفشل كان بيفسد الترانزاكشن، فكل الصفوف
> اللي بعده بتفشل بـ«current transaction is aborted». غلطة في صف ٣ كانت
> بتضيّع ١٩٩٧ صف سليم من غير ما حد ياخد باله.

**الحارس**: `npm run verify:import-capacity`

### ٣) التقارير بقى ليها فترة
`src/server/services/reportPeriod.ts`

- الافتراضي **٩٠ يوم**، الأقصى **٤٠٠ يوم**، وفيه مُختار فترة في شاشة التقارير
- بيتطبّق على: ربحية التجار · أداء المناديب · الأرباح والخسائر · الإيرادات بالنوع
- **ميزان المراجعة** فضل تراكمي — طبيعته كده وتحديده بفترة يخلّيه غلط محاسبيًا
- **عهدة المناديب والعمولات المستحقة** فضلوا تراكميين — دول أرصدة جارية مش أداء فترة

### ٤) الفهارس الناقصة
`src/server/db/migrations/0025_perf_indexes.sql`

| الفهرس | بيخدم إيه |
|---|---|
| `shipments (created_at DESC, id DESC)` | الشاشة الرئيسية |
| `shipments (status, created_at DESC, id DESC)` | الشاشة بفلتر حالة |
| `shipments` trgm على `awb` و`recipient_phone` | البحث بالاحتواء |
| `shipment_status_history (shipment_id, to_status, occurred_at)` | «امتى اتسلّمت من التاجر؟» |
| `journal_entries (entry_no DESC)` | دفتر اليومية (bigserial مش بيعمل فهرس) |
| `journal_lines (account_id, entry_id)` | رصيد التاجر والعهدة |
| `notifications (user_id, created_at DESC)` | بولنج الإشعارات كل ٢٠ ثانية |
| ~~`jl_courier_idx`~~ | **اتشال** — بيتكتب وعمره ما اتقرا |

### ٥) الحوض والمهلات
`src/server/db/index.ts`

- `DB_POOL_MAX` من ١٠ لـ**٢٠**
- `statement_timeout` **٣٠ ثانية** · `lock_timeout` **١٠ ثواني** ·
  `idle_in_transaction_session_timeout` **٦٠ ثانية**
- المهلات بتتبعت كبارامترات بدء الاتصال → بتتطبّق على **التطبيق بس**؛
  الهجرات والباك أب بيفتحوا عملاءهم الخاصة وماتتأثرش
- `PGBOUNCER=1` بيقفل الـ prepared statements (شرط وضع تجميع الترانزاكشن)

### ٦) مسارات أخف
- **كشف الحساب** بقى **قراءة بحتة** — كان بيفتح ترانزاكشن كاتبة في كل فتحة
  صفحة وبيتنافس على نفس قفل صف التاجر مع التسليمات الجارية
- **التسوية** استعلامين لكل ٥٠٠ صف بدل استعلامين **لكل شحنة**
  (تاجر عليه ٣٠٠٠ أوردر: من ٦٠٠٠ ذهاب وعودة لـ١٢)
- **المؤشر** بقى `(created_at, id)` — الاستيراد بيعمل صفوف بنفس الثانية،
  فالمؤشر على `created_at` لوحده كان بيتخطّى صفوف أو يكرّرها
- **فشل الإشعارات** بقى بيتسجّل بدل ما يتبلع بصمت

## إزاي تثبته بنفسك

```bash
# ١) قاعدة منفصلة بمليون شحنة (= ١٠٠ يوم × ١٠ آلاف)
npm run seed:load -- --shipments=1000000

# ٢) شغّل السيرفر عليها (staging والإنتاج مابيتلمسوش)
DATABASE_URL=postgres://…/tewsal_load npx next start -p 3200

# ٣) قيس
BASE=http://127.0.0.1:3200 npm run bench:load -- --seconds=30 --concurrency=20
```

**الأهداف**: جدول الشحنات p95 < 300ms · التتبع < 500ms · الأخطاء < ١٪.

## اللي لسه مؤجّل (بقرار، مش نسيان)

| البند | ليه مؤجّل |
|---|---|
| **التقسيم الشهري (partitioning)** | محتاج تعديل الـtriggers الـappend-only اللي بتحمي الدفتر. يتعمل على **نسخة مسترجعة الأول**، مش على قاعدة شغّالة. الفهارس + حدود الفترة بيكفّوا لحد ما الجداول تعدّي عشرات الملايين. |
| **BullMQ للفان-آوت** | محتاج **Redis** مش متركّب. الحالي بيعمل استعلامين زيادة بعد التحويل — مش ٦٠ ألف مهمة زي ما كان متوقّع. الفشل بقى **بيتسجّل** بدل ما يتبلع، فلو بقى مشكلة هتبان. |
| **trigger التوازن statement-level** | Postgres **مايسمحش** بـ`CONSTRAINT TRIGGER` على مستوى الجملة — والتأجيل للـCOMMIT هو اللي بيخلّي القيد غير المتوازن مستحيل. الفحص بيتم على ٤ صفوف عبر فهرس، يعني ميكروثواني. **مش هنكسر أهم حارس في السيستم عشان مكسب مش موجود.** |
